## 0. 这份文件如何使用

这不是一般性的内容建议，而是一份可以直接交给 Skywork 的制作规格书。建议按以下顺序使用：

1. 先把本文件和以下资料上传给 Skywork：
   - `Careloop_Maker_in_China_HK_2026_PPT_Optimization_Guide.docx`
   - 旧版 `Group 5-暖桌Careloop.pdf`
   - 参考样本 `TeaVita AI--Maker in China.pdf`
   - 当前 project 的 UI 截图或录屏
   - 当前 project 的 README、测试结果、构建结果和可展示的 API/UI 资料
2. 复制第 2 节「总控 Prompt」，让 Skywork 先生成完整 PPT 初稿。
3. 根据第 4 节的逐页规格，逐页检查内容、图片和事实边界。
4. 如果 Skywork 生成的页面过于拥挤，复制第 5 节「二次优化 Prompts」。
5. 最后复制第 6 节「事实核查与提交前自检 Prompt」，让 Skywork 做最终审稿。

如果 Skywork 无法读取本地路径，请把文件直接上传；如果无法访问当前 project，请用真实 UI 截图替换所有 `[[待填]]` 占位符。禁止让 Skywork 自行编造截图、数据、用户数量、收入、试点或合作方。

## 1. 项目和生成边界

### 1.1 项目定位

Careloop 是一个面向社区餐饮/照护场景的多角色点餐与履约协作系统，帮助长者、家属、工作人员和厨房围绕同一份订单完成：

> 说出需求 → 系统理解 → 用户确认 → 厨房接单 → 配送/取餐状态 → 异常时转人工。

本次 PPT 的主角是「当前可运行的软件 Demo 和新版 UI」，不是旧版木板模型，也不是尚未部署的自动烹饪、传送带或机器人系统。

### 1.2 目前必须诚实表达的状态

以下内容必须明确写成当前边界，不得隐藏或改写成成果：

- 当前已有可运行的端到端原型。
- 当前可展示新版 UI、语音/文字输入、订单确认、工作人员协助、厨房状态和配送状态等流程。
- 当前 project 有工程验证证据：`2 个测试文件、9 个测试通过`；如实际结果已经变化，以最新真实结果替换。
- TypeScript build 和 lint 可作为工程证据；如果最新执行结果不同，以最新结果替换。
- 支付、AICAN、传送带或真实物理设备如仍是 adapter/mock，必须标注为 `DEMO ASSUMPTION` 或 `DEMO ADAPTER`。
- 当前没有真实线下试点、真实订单量、真实收入、复购率、客户合同或真实单位经济数据。
- 赛后香港场景验证只能写成 roadmap / TO VALIDATE，不能写成已经落地。

### 1.3 PPT 的唯一任务

让评委在 7 分钟内记住四件事：

1. Careloop 为谁解决什么具体问题；
2. 当前 Demo 已经跑通了什么；
3. 当前还没有验证什么；
4. 为什么值得在香港继续验证，以及团队希望获得什么帮助。

### 1.4 禁止事项

Skywork 不得自行生成或暗示以下内容：

- “已有数百名用户”“已有多个社区使用”“已有收入”；
- “准确率 100%”“节省 70%”“15 单/日”“8 个月回本”等无来源数字；
- “已在香港落地”“已与某机构合作”等未经提供证明的表述；
- 真实厨房已经自动烹饪、真实传送带已经运行、真实支付已经完成；
- 未来路线图中的试点被写成当前成果；
- 以 AICAN 或其他视觉素材替代真实 Careloop UI；
- 生成无法在当前 project 中复现的按钮、流程或功能。

```text
- 必须作为 TO VALIDATE 的内容：真实用户偏好、实际使用频率、准确率、人工介入率、复购、收入、单位经济、合作方意愿、赛后试点成果。

【不可出现的主张】
- 不得写“已有真实用户/订单/收入/合作社区”，除非资料中提供可核验的证明。
- 不得把赛后 roadmap 写成已经发生的试点。

- 不得使用无来源的巨大 KPI 数字。

【设计方向】
- 风格：可信、温暖、克制、产品化、适合香港创客比赛。
- 颜色：以当前 UI 的青绿色/深色为产品主色，保留少量暖桌的珊瑚红作为强调色；每页最多 2 个强调色。
- 版式：一页一个结论，标题必须是结论句，不要使用空泛标题如“Core Validation Metrics”。
- 视觉主角：当前 Careloop UI 截图、订单状态和用户动作；不要用旧木板模型、泛化 3D 概念图或不相关的自动烹饪图片作为主视觉。
- 页面信息密度：每页最多 1 个主结论、3 个以内支撑点、1 个主要图表/流程/截图区域。
- UI 截图必须裁切放大，保证按钮、状态和订单结果在投影上可读；禁止把完整网页缩小成看不清的长截图。
- 使用中文短句，减少长段落；尽量以流程、对比、状态卡片和证据表替代文字墙。

【输出前自检】
请在生成 PPT 后逐页检查：
1. 第 1 页能否在 10 秒内说明 Careloop 是什么；
2. 第 4-6 页是否使用当前新版 UI；
3. 是否有一条订单贯穿语音/文字、预览、确认、厨房、配送和人工兜底；
4. 是否明确写出当前没有线下试点；
5. 是否删除无来源数字和未经证明的商业成果；
6. 是否清晰区分 VALIDATED、EXTERNAL SOURCE、DEMO ASSUMPTION、TO VALIDATE；
7. 是否有明确的香港站 Ask；
8. 是否可以在约 7 分钟内完成讲述。

先输出“页面目录 + 每页一句话结论 + 需要我补充的素材清单”，再生成 PPT 页面。
```

## 4. 14 页主 PPT 逐页生成规格与 Prompts

以下每页 Prompt 可单独复制给 Skywork，用于重做或修正特定页面。每页均要求同时输出：页面内容、视觉布局、演讲备注、事实标签。

### 第 1 页｜封面：一句话说清 Careloop

**页面结论**：Careloop 是一个让社区餐饮更容易被长者使用的点餐与履约协作系统。

```text
请生成第 1 页封面。

标题：Careloop：让社区餐饮更容易被长者使用
副标题：语音/简单界面发起订单，家属、工作人员与厨房共同完成确认与履约
状态短句：当前阶段：可运行软件 Demo｜尚未进行线下试点
必须使用的视觉：当前 project 的 UI hero 截图，优先使用老人模式或订单确认页面；如果没有真实截图，放“待补真实 UI hero”占位框，不要生成假 UI。
视觉布局：左侧标题和一句话定位，右侧大幅 UI 截图；底部只放 Careloop、Maker in China Hong Kong 2026 和 VALIDATED/TO VALIDATE 标签。
删除：成员姓名、演讲分工、旧木板模型、过大的英文口号、无关 3D 图。
讲稿备注：30 秒内说清产品是什么、当前能展示什么、当前还没有线下试点。
```

### 第 2 页｜问题：点餐、等待和照顾不连续

**页面结论**：问题不是“没有饭”，而是长者在表达需求、确认订单和等待履约时容易被系统门槛卡住。

```text
请生成第 2 页“问题场景”。

主标题：问题不是没有饭，而是点餐、等待和照顾不连续
请用一个具体的、可理解但不虚构的场景串联三方：
- 长者：看不清、听不清或不确定自己是否下单成功；
- 家属：想代点，但无法确认长者真正需要的菜品、口味和收餐信息；
- 社区食堂/工作人员：需要处理模糊订单、重复确认和异常情况。

视觉：用一条横向用户旅程或三张角色卡，不要用三段长文字。
每张角色卡最多 2 个短句。
如果要引用香港/养老/数字无障碍数据，只能使用已上传的公开来源，并在数字旁写来源名称和年份；没有来源就不放数字。
页面标签：EXTERNAL SOURCE（仅用于外部资料）+ TO VALIDATE（用于用户问题假设）。
禁止：写“香港有 X 万老人因此一定需要本产品”、写未经来源支持的痛点比例。
讲稿备注：40 秒，强调“流程断裂”而不是泛泛讲养老很重要。
```

### 第 3 页｜缺口：现有方案各自解决一段

**页面结论**：传统食堂、复杂 App 和家属代点分别解决局部问题，但缺少一条可确认、可追踪、可转人工的订单链路。

```text
请生成第 3 页“现有方案缺口”。

标题：为什么现有方案仍然有门槛
做三列对比：
1. 传统柜台/电话：有人情味，但记录、确认和状态追踪弱；
2. 通用点餐 App：效率高，但对部分长者的操作和识别门槛高；
3. 家属代点：能解决操作问题，但需求确认、状态同步和异常处理不连续。

右下角用一句结论收束：Careloop 将“表达需求—确认—履约—兜底”放在同一条订单链路中。
每列最多 3 个短点；不要使用夸张的红叉或贬低现有方案。
视觉：三列卡片 + 中间或底部一条 Careloop 闭环箭头。
标签：TO VALIDATE；如使用外部数据，另加 EXTERNAL SOURCE。
讲稿备注：35 秒，说明 Careloop 不是要替代工作人员，而是减少重复确认和无状态订单。
```

### 第 4 页｜产品总览：四个角色，一条订单

**页面结论**：Careloop 的核心不是四个独立页面，而是四个角色围绕同一份订单协作。

```text
请生成第 4 页“产品总览”。

标题：新版 Careloop：四个角色，一条订单闭环
角色：
- 长者：用语音或简单 UI 表达需求；
- 家属：远程协助或代点，并查看订单状态；
- 工作人员：处理不确定、异常和人工确认；
- 厨房/配送：接收已确认任务并更新状态。

在页面中心放一份订单对象，四个角色围绕它连接；不要画成复杂生态系统。
底部用 5 个动作节点：表达 → 预览 → 确认 → 履约 → 兜底。
视觉必须突出“同一订单状态在不同角色间同步”。
如果没有统一订单状态截图，使用简洁流程图，不要自造产品页面。
标签：VALIDATED（当前实际存在的流程）+ DEMO ASSUMPTION（演示用角色/状态）。
讲稿备注：45 秒，先讲产品如何工作，再讲技术。
```

### 第 5 页｜新版 UI：三种模式

```text
请生成第 5 页“当前新版 UI”。

标题：真实 UI：老人模式、家属代点、工作人员模式
使用三张真实截图并放大裁切：
1. 老人模式：突出大按钮、语音/文字双通道、确认前预览；

3. 工作人员模式：突出异常处理、人工确认和订单接管。

每张截图旁只配一句动作句：

不要把完整网页缩成小图；每张截图只展示 1 个关键动作。
如果截图缺失，使用“待补真实截图”占位框并列出文件名。
标签：VALIDATED；如果截图中有模拟数据，旁边小字 DEMO ASSUMPTION。
讲稿备注：40 秒，只讲页面如何降低操作门槛，不逐一念 UI 文案。
```

### 第 6 页｜90 秒 Demo：一条订单贯穿全流程

**页面结论**：Demo 证明的是订单流程可运行，不是已经完成真实社区运营。

```text

标题：90 秒 Demo：从一句话到一份可履约订单
请用时间线或 6 格连续画面展示这一条演示订单：

2. 系统显示识别结果和可能的不确定项；
3. 用户确认订单；
4. 订单进入厨房任务；

每个节点只放截图、动作和状态，不写长段解释。
给以下内容加清晰标签：
- 真实可展示 UI：VALIDATED；
- 菜单、桌号、配送状态：DEMO ASSUMPTION；
- 真实厨房/真实配送：不要声称已发生。

如果有录屏，页面右上角放 QR/视频入口；同时保留连续截图，以便离线演示。
讲稿备注：90 秒，正常路径约 60 秒，异常转人工约 30 秒。
```

### 第 7 页｜技术闭环：理解、确认、履约、兜底

**页面结论**：Careloop 的技术价值在于把 AI 识别放进一个有确认机制和人工兜底的订单状态机，而不是只展示一个聊天框。

```text
请生成第 7 页“技术闭环”。
```

```text
如果有任何一项不满足，请先输出问题清单和修改方案，不要直接说“可以提交”。
```

## 8. 推荐的 Skywork 操作顺序

### 第一次生成

1. 上传所有资料；
2. 发送第 2 节总控 Prompt；
3. 让 Skywork 先只输出页面目录、页面结论和素材缺口；
4. 补齐真实 UI 截图、测试结果和团队资料；
5. 让 Skywork 生成 14 页主 PPT + 附录。

### 第二次修改

按以下优先级修改，不要一开始纠结装饰：

1. 事实边界；
2. 产品叙事；
3. 一条订单 Demo；
4. 当前 UI 的可读性；
5. 工程证据；
6. 香港赛后验证路线；
7. 视觉统一。

### 第三次修改

复制第 7 节的三个审稿 Prompt：

1. 反幻觉事实核查；
2. 7 分钟核查；
3. 评委压力测试。

最后再让 Skywork 输出：

- 比赛提交版 PDF；
- 可编辑源文件；
- 7 分钟讲稿；
- 90 秒 Demo 口播；
- 预录 Demo 备用版；
- 一页技术事实表；
- 一页赛后验证路线图。

## 9. 交付前人工确认表

Skywork 生成后，团队必须人工确认以下内容，不能完全依赖 AI：

- 每一个按钮、菜品、桌号、订单状态是否真的存在于当前 Demo；
- 测试通过数量是否为最新结果；
- build/lint 截图是否来自当前版本；
- 语音输入失败时是否真的能展示转人工路径；
- 现场网络不可用时是否有录屏或连续截图；
- UI 截图是否包含个人资料、密钥或不应公开的信息；
- 所有团队姓名、学校、机构、联系方式是否准确；
- 所有外部资料链接是否可打开；
- 讲稿中是否仍有“已经落地”“已经验证”“已有用户”等未经证明的表述；
- 第 14 页 Ask 是否是团队真正希望获得的帮助。

最终原则：

> 内容可以暂时不完整，但不能把未知写成已知；Demo 可以是模拟的，但必须把模拟边界说清楚；没有线下试点不是缺陷，隐瞒没有试点才会损害可信度。
