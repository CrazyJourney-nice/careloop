## 1. 单元测试

- 识别意图枚举和 Zod schema 校验。
- 数量：一份、两份、数字和缺省数量。
- 菜品精确名称、别名、同音候选和不存在菜品。
- 少盐、不辣、少油、易咀嚼等字段映射。
- 多菜品和修饰词归属。
- A01、A12 等桌号解析和非法桌号拒绝。
- 空文本、取消、确认、请求工作人员。
- 置信度分级和候选排序。

## 2. 集成测试

- `/api/orders/voice-preview` 不产生订单副作用。
- 预览确认后才能写入订单明细。
- 低置信度结果能创建工作人员会话但不能进入后厨。
- 语音口味字段在订单、后厨任务和事件中保持一致。
- 会话过期后不能继续确认。
- WebSocket 能收到预览、工作人员接管和订单状态事件。
- 重复提交幂等，不产生重复订单。

## 3. 端到端场景

### 场景 A：普通话清晰表达

“我要一份少盐的番茄炒蛋，A12桌。”应展示菜名、数量、少盐和 A12，点击确认后加入草稿。

### 场景 B：复杂表达

“来两份不辣的鱼，再加一碗粥，鱼要软一点。”应将不辣和易咀嚼仅绑定到鱼，不绑定到粥。

### 场景 C：方言或吐字不清

返回多个候选时，用户可以点击正确菜品；点击“都不是”两次后进入工作人员协助。

### 场景 D：识别失败

拒绝麦克风、空文本、超时和不支持浏览器都能回到手动点餐，不出现白屏。

### 场景 E：订单闭环

语音预览 → 用户确认 → 订单确认 → 支付方式 → 后厨 → 配送，所有页面显示的结构化口味一致。

## 4. 验收门槛

- 核心单元和集成测试全部通过。
- 现有 `npm run lint`、`npm run test`、`npm run test:integration`、`npm run test:e2e` 通过。
- 至少在 Chrome 桌面、Android Chrome 或同等 Chromium 平板环境验证。
- 无权限、低置信度、方言、噪声和重复提交流程均有可见反馈。
- 不允许出现“语音识别结果未经确认直接下单”。
